Büyük resim

Bir kurum siparişlerini daha iyi yönetmek istesin. SAD önce neyin düzelmesi gerektiğini sorar. SDLC bu işi evrelere ve belgelere ayırır. Waterfall bu evreleri sırayla, Iterative tekrarlarla yürütür. Agile, XP ve Scrum çalışan üründen erken geri bildirim toplar.

Sonra “Kaç kişi, ne kadar süre?” sorusu gelir. LOC, FP, COCOMO ve Engineering rules tahmin üretir; Scheduling ve Critical path işleri zamana bağlar. Doğru şeyi tahmin edebilmek için önce Requirements gerekir. FR hizmeti, NFR kaliteyi ve koşulları anlatır. Fishbone nedenleri araştırır; Fact-finding kullanıcıdan kanıt toplar.

Use case bu ihtiyaçları aktörün amacı ve adımlarıyla yazar. User story küçük bir kullanıcı faydasına odaklanır. Design ihtiyacı teknik yapıya çevirir. UML ile akışı Activity, mesajları Sequence, durumları State machine, nesne yapısını Class, parçaların sözleşmelerini Component diagram üzerinden okuruz. Yedi bölüm aynı sistemin farklı sorularını cevaplar.

Konu kartları

SAD ve dört P

Ch1 · 8, 17–25

Bir kurumun işini iyileştirmek için önce ihtiyacı anlarız, sonra çözümü kurarız.

Kâğıda yaz
  1. Software Engineering: systematic, disciplined, quantifiable
  2. Analysis → what; Design → how
  3. People · Product · Project · Process
  4. Information System: hardware, software, data, process, people

Şık tuzağı: Product = code only yanlış; belgeler de ürüne dahildir. Process evrelerin sırasını, sıklığını ve çıktılarını belirler.

Stakeholders

Ch1 · 27–35

Aynı sisteme herkes başka bir soruyla bakar: kim öder, kim çözer, kim kullanır?

Kâğıda yaz

  2. Project manager: schedule, budget, quality
  3. Systems analyst: problems, opportunities, directives
  4. System designer: technical solution; System builder: construction
  5. Software tester: defects; System user: daily interaction

Şık tuzağı: Stakeholder = user only yanlış; sistemde çıkarı olan herkes kapsama girer.

SDLC ve belgeler

Ch2 · 4–40

Her evre bir sonraki evrenin kullanacağı somut bir çıktı bırakır.

Kâğıda yaz
  1. Planning → SPMP: scope, feasibility, resources, schedule, cost
  2. Requirements Analysis → SRS: what to build
  3. Software Design → SDD: how to build
  4. Development → program code; Testing → tested system
  5. Deployment → delivered system, release description, trained users
  6. Maintenance: fixes, enhancements; outputs = those of the related phases

Şık tuzağı: SRS = how to implement yanlış; nasıl sorusunun teknik karşılığı SDD içindedir. Planning tahminleri proje boyunca güncellenir.

Waterfall ve Iterative

  2. Feedback loops: adjacent phases in practice
  3. Iterative: analysis, design, development, testing in each iteration
  4. Prototyping · Spiral: process models listed in Ch2

Şık tuzağı: Iterations must be serial yanlış; slayt ayrı takımlarla paralel geliştirmeye izin verir. Prototyping ve Spiral için slaytta verilmemiş ayrıntılar eklenmedi.

Extreme Programming (XP)

Şık tuzağı: TDD = code first yanlış; önce başarısız test yazılır. Ch3 s26, Sustainable pace yanında sürüm sonu aşırı çalışma cümlesi de içerir; tutarsız ifadeyi genel kural yapma.

LOC ve FP

Ch3 · 48–52; Ch4 · 3–5, 31–34

Kâğıda yaz
  1. LOC: physical, technology dependent; KLOC = LOC / 1000
  2. FP: functional size, technology independent
  3. Gearing factor: LOC per FP
  4. Duration: months; Effort: person-months

Şık tuzağı: FP counts programming functions yanlış; kullanıcı düzeyindeki işlevi sayar. LOC karşılaştırmasında boş satır ve yorum sayma kuralları aynı olmalıdır.

FP: neyi sayıyoruz?

Ch4 · 9–25

Önce sınırı çiz; sonra sınırdan geçen işi ve tutulan veriyi ayır.

Kâğıda yaz
  1. EI: outside → inside; add/change/delete
  2. EO: derived data → outside
  3. EQ: retrieve data
  4. ILF: logically related data inside boundary
  5. EIF: reference data; another application’s ILF
  6. FTR: files referenced; DET: recognizable fields; RET: data subgroup

Şık tuzağı: EIF = internally maintained file yanlış; başka uygulamanın verisine başvurulur. Başka uygulamadan veri çekip kaydetme hem EQ hem EI sayısını artırabilir.

FP: ağırlık ve düzeltme

Ch4 · 14–30

Her sayımı karmaşıklığıyla çarp; sonra sistemin genel özelliklerine göre düzelt.

Kâğıda yaz
  1. UFP = Σ(count × complexity weight)
  2. VAF = Σ GSC weights (slides’ notation)
  3. GSC: none 0, incidental 1, moderate 2, average 3, significant 4, essential 5
  4. AFP = UFP × (0.65 + 0.01 × VAF)

Şık tuzağı: VAF = 1.05 bu slaytların adlandırmasında yanlış; hava durumu örneğinde VAF = 40, çarpan 1.05’tir.

Estimation modelleri

Ch4 · 32–43

Aynı boyut için iki ayrı yöntem iş yükü tahmini verir; ağırlıkla birleştirebilirsin.

Kâğıda yaz
  1. Organic: small, known environment; Semi-detached: medium/web
  2. Embedded: tight hardware–software constraints
  3. COCOMO I: E = a × KLOC^b; D = c × E^d
  4. Engineering rules: D = FP^A; Staff = FP/150; E = Staff × D
  5. Simple: A=.32; Average: A=.40; Complex/Embedded: A=.45
  6. Size: <500 simple; 500–999 average; ≥1000 complex

Şık tuzağı: 500 FP = simple yanlış; sınır dahil olduğundan average. Türüne göre standalone basit, web/mobile/client-server orta, embedded karmaşıktır. COCOMO II adı geçer; bu kapsamda sayısal katsayı eklenmedi.

Critical path

Ch4 · 54–65

Bir işin gecikmesi bütün bitişi geciktiriyorsa o işin zaman payı yoktur.

Kâğıda yaz

  2. TL: min(successor TL − successor duration)
  3. Slack = TL − TE

Şık tuzağı: Shortest path yanlış; en uzun bağımlı yol projenin en erken bitişini belirler. Birleşmede ileri giderken en büyük, geri giderken en küçük değeri seç.

State machine diagram

Ch7 · 33–50

Tek bir varlığın olaylara göre hangi durumda kaldığına bak.

Kâğıda yaz
  1. State: invariant situation; Transition: state change
  2. Simple state: no substates; Composite state: substates
  3. Region: states and transitions; concurrent regions
  4. Initial pseudostate · Final state · Fork / Join
  5. Shallow history: re-enter last active substate
  6. Behavioral: discrete behavior; Protocol: usage lifecycle

Şık tuzağı: State = message order yanlış; mesaj sırası Sequence bakışıdır. ATM örneğinde exit / ejectCard, çıkışın nedeni ne olursa olsun çalışır.

Kâğıda yaz

  2. Provided interface: ball, complete circle
  3. Required interface: socket, half circle
  4. Port: interaction point
