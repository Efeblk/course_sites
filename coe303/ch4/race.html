Race Condition Stepper

Misconception #4: "counter++ is atomic." It is three machine instructions — load, add, store. Two threads sharing counter can interleave them and lose updates.

1 · You are the scheduler

Thread A and thread B each run counter++ once. Start: counter = 0. The right answer is 2. Pick who runs each instruction.

2 · Now do it a million times (slide 55)

int counter = 0;
void *worker(void *arg) {
    for (int i = 0; i < N; i++)
        counter++;          /* NOT atomic — lost updates! */
    pthread_exit(NULL);
}
/* two threads run worker(): counter ends up < 2 × N */
Press Run.

This is a simulation of instruction interleaving, not real threads — real loss rates depend on the CPU, but the effect is the same. Try it for real in your Ubuntu VM: gcc -pthread race.c -o race, or detect it with -fsanitize=thread.

3 · Why the slide-29 array sum is safe

In the Pthreads sum example each thread writes only partial[tid] — its own slot — and main adds the partial sums after pthread_join. No two threads write the same variable, so there is no race. If every thread did total += s on one shared global instead, you would get exactly the lost updates above (end-of-session thinking question Q1). The real fix — mutexes — is Chapter 6.
